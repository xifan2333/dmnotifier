# TTS 流式播放验证记录

2026-10-08，Linux 本机验证。临时 Go 测试通过 `go test -overlay` 注入，未在仓库新增测试文件；临时工具位于 `/tmp/dmnotifier-stream-verification`，不作为项目依赖。

## 功能检查

- MiMo 模拟 SSE：两个请求并发；服务端仍保持响应打开时，前缀已经送入播放器；正文在前缀之后播放；正文开头的 `(开心)` 标签原样提交。
- 前缀缓存命中后不再请求；LRU 容量、单项上限及淘汰行为通过检查。
- 停止订阅中断阻塞请求和播放器；SSE 缺少结束标记、API 错误、正文先失败均正确结束当前播报，不从头重播。
- Edge 本地 WebSocket：取消会关闭阻塞读取中的连接；收到部分音频后断线仍返回错误。测试只在临时 overlay 中替换连接地址。
- TUI 的 provider 往返切换保持两套音色配置；旧配置缺省值可正常显示及编辑。
- afplay 回退路径输出有效 WAV，并保持前缀和正文顺序；在 Linux 上使用替身验证文件内容，未在 macOS 声卡上实播。
- mpv 实际音频输出、ffplay 对 PCM16/MP3 的解码播放均成功。发现并修复 ffplay 新版本不再接受 `-ac` 的兼容问题。
- Edge 实际云端调用成功；SDK 的 Chromium 兼容版本由 130 更新至 143 后，原先的握手拒绝消失。

## 延迟记录

播放器启动使用 mpv IPC 的 `playback-restart` 事件观测，代表播放器开始输出，不是麦克风回录的声学延迟。网络首包和播放器延迟分别记录，单次结果不构成性能保证。

| 场景 | 请求至首音频 | 请求至流结束 | 首包至播放器开始 | 流结束前播放 |
| --- | ---: | ---: | ---: | --- |
| 本地 PCM，首段 9600 字节，后续每 100ms 输入 | 本地输入 | 持续分段输入 | 47ms | 是 |
| 本地 MP3，每 100ms 输入 1200 字节 | 本地输入 | 持续分段输入 | 619ms | 是 |
| Edge 云端短句 | 1936ms | 2091ms | 286ms | 否，短句生成先完成 |
| Edge 云端长句 | 2685ms | 3396ms | 105ms | 是 |

本地 SSE 测试在空闲时记录前缀响应头约 4ms、首音频约 67ms（服务端故意延迟 60ms）、请求约 69ms；首音频至写入播放器约 0.08ms。正文约 8ms 返回首音频，首次交付等待前缀约 61ms。并行交叉编译造成负载时，对应数据会明显增加。

`on_timing` / `slog.Debug` 的 `first_write` 只表示首次写入播放器；`request` 包含消费背压等待；`headers` 目前仅 MiMo 可用。`phase=synthesis` 和 `phase=delivery` 分别记录请求完成和首次交付。缓存命中无需网络请求。

200ms 是优化目标：Edge 长句和本地 PCM 样本达到目标，Edge 短句及慢速小包 MP3 样本未达到。MP3 的帧解析、播放器启动和声卡缓冲仍会增加等待。
